# 移魂大法（移魂 / 夺舍）：把一台电脑上的 DSH 搬到另一台

2026-11-17 第三版（经独立审核修正）。**尚未实现。**

> **硬约束（用户明确要求）**：功能必须**自包含**。默认用户机器上没装任何参考插件
> （`dsh-config-manager`、`dsh-chat-import`），所以：
> - **不得**把"先安装参考插件"写进流程；
> - 需要的能力自己实现；参考插件只作设计参照与代码来源；
> - 两者均为 **MIT**，若借鉴代码须保留其版权与许可声明。

## 零、审核推翻的三个前提（本版据此重写）

| 我原来的写法 | 实际情况 | 影响 |
|---|---|---|
| 结构层 = 复制 `profiles/<p>/cordis.yml` | **它是 `[]`**，注释明写"改 `cordis.patch.yml`，别改这个文件"。真正的组合在 `package.json` 的 **`dsh.profile.bundles`（有序）** + `dependencies` | 照原方案实现会搬一个空文件，等于没搬 |
| 配置层读 `settings.yaml` | **它是过期货**。首次启动已把内容导入 profile patch，文件改名为 `settings.yaml.imported`；本机实测它与生效值不一致 | 读它会拿到错值 |
| 插件重装调 `dsh plugin --profile add` | PATH 上那个 `dsh` 是 **0.2.0-rc.1**，运行中的是 **0.2.2-rc.3** | 版本错配写入，可能写坏 profile |

**结论：全部改走进程内服务。** 不裸写文件、不调外部 CLI。

**第四处（知识库 X 官方文档核对后新增）**：我原来写「patch 只合并不重建」——**这也错了**。
官方限制明写：**用户补丁是整体替换、非深 merge**。所以导入 patch 只有两种正确做法：
① 整份替换（替换前必须备份）；② 用 `ctx.configEditor.edit()` 逐条改。
**不存在「把两份 patch 合并起来」这条路。**

## 一、要搬的到底是什么

| 层 | 内容 | 谁来搬 |
|---|---|---|
| **结构层** | `package.json` 的 `dsh.profile.bundles`（有序）+ `dependencies` | 我们，经 `ctx.pluginManager` |
| **配置层** | 各条目 `config`（生效值）+ 提示词 + 预设 + `AGENTS.md` + 技能 | 我们，经 `ctx.settings` / `ctx.configEditor` |
| **插件层** | 插件清单与来源 | 我们，经 `ctx.pluginManager.installBundle` |
| **记忆层** | 会话 + **附件** + 工作区归属 | 我们，同版本复制文件；跨版本走服务重建 |
| **凭据层** | `~/.dsh/.credentials.yaml` 里的值 | **只能人来做** |

## 二、术语先说清（避免再踩）

- **档案（profile）**：一套 DSH 配置组合，本机有 `desktop` / `web` / `headless`。
- **组合**：哪些 bundle、按什么顺序加载，记在 `package.json` 的 `dsh.profile.bundles`。
- **patch**：`cordis.patch.yml`（home 层 + profile 层），一条条改配置或插条目；**整份替换、非深 merge**。
- **bundle**：一个可安装的包，自带 patch。

## 三、包长什么样

默认是**目录**（会话和附件合计数 GB，目录便于挑选、续传、人工核对）：

```text
soul-20261117/
├─ manifest.json          来源机器、profile、DSH 版本、生成时间、分区清单、体积
├─ integrity/checksums.json
├─ profile/
│   ├─ bundles.json       有序 bundle 列表 + 各自版本（真正的"结构"）
│   ├─ dependencies.json  package.json 的 dependencies
│   └─ patches/           home 层与 profile 层 patch（原样）
├─ settings/
│   └─ namespaces.json    describe({redactSecrets:true}) 的结果：ns / value / revision
├─ custom/
│   ├─ AGENTS.md  skills/  prompts.json  agent-presets/
├─ plugins/
│   ├─ installed.json     name / version / spec
│   └─ local-plugins/     link:/file: 来源的 npm pack 产物（可选）
├─ workspaces/
│   └─ workspaces.json    path / title / sessionIds
├─ sessions/              可选：同版本直接复制会话文件
├─ attachments/           可选但强烈建议：内容寻址，路径无关，直接按对象树复制
└─ credentials/
    └─ secrets.enc        可选：AES-256-GCM，密码只由人输入
```

## 四、导出（A 端）

1. **读环境**：`$DSH_HOME`、当前 profile、DSH 版本、Node 版本（版本要写进 manifest 并在导入时比对）；
2. **结构层**：`ctx.pluginManager.listBundles()` 取有序列表与版本；`package.json` 取 dependencies；
3. **配置层**：
   - `ctx.settings.describe({ redactSecrets: true })` 逐个 namespace 取生效值与 revision；
   - patch 层原样复制（两层分别存）；
   - `AGENTS.md`、`skills/`、`.agent-presets/`、提示词逐文件复制；
4. **插件层**：已装清单 + 来源；`link:`/`file:` 的跑 `npm pack` 带上；
5. **记忆层**（用户勾选）：
   - **同版本**：直接复制 `sessions/` 与 `attachments/`（更快、更保真、零格式风险）；
   - **跨版本**：走服务读出事件流再重编码（见七、跨版本迁移）；
6. **写 manifest 与校验和**；
7. **体量闸门**：本机实测 `sessions/` 2.59 GB、`attachments/` 606.7 MB。导出前先报体积，让用户选
   「只带结构+配置」「带最近 N 个会话」「全带」。

## 五、注入（B 端）

前提：B 端已装 `dsh-everywhere`——它自己就是入口。

1. **体检**：校验和、DSH/Node 版本比对、目标 profile 是否已有同名组合、缺哪些依赖；
2. **计划（dry-run）**：逐条列出「装哪个包 / 启用哪个 bundle / 写哪个 settings 条目 / 复制哪些文件 /
   哪些项会被跳过」，给 `planId` 与指纹；
3. **快照**：`package.json`、`pnpm-lock.yaml`、两层 patch、涉及到的 settings 条目旧值、将被覆盖的会话与附件；
4. **执行（顺序固定，全部走服务）**：
   1. **先装包**：`ctx.pluginManager.installBundle(spec)`（带锁、带回滚、registry 兜底）；
   2. **再启用 bundle**：`ctx.pluginManager.setBundleEnabled(name, true)`，按 manifest 里的**顺序**；
   3. **最后写配置**：
      - settings 用 `ctx.settings.replace(ns, value, expectedRevision)`——注意 `replace` 的语义是
        「先把活动字段重置为继承值，再应用提交字段」，不是打补丁；
      - patch **整份替换**（先备份）或用 `ctx.configEditor.edit()` 逐条改；**官方明确是整体替换、非深合并**；
   4. 记忆层：复制会话与附件 → **`workspaceRegistry.create/attachSession` 把会话挂到工作区**；
5. **自检**：把写的 patch 解析回读一遍（**空文件或只有注释会让 DSH 起不来**）；settings 的 revision 与值复核；
6. **收尾**：如实报告「哪些已即时生效 / 哪些需要刷新页面 / 哪些需要重启 DSH」；
7. **凭据**：人工输密码，逐条 `ctx.credentials.set(ref, value)`，失败逐条报告。

硬失败 → 逆序回滚到快照；装包失败按警告处理并逐条列出（`pluginManager` 自己会恢复 `package.json` 与 `pnpm-lock.yaml`，这点要记进结果）。

## 六、路径映射

- **工作区路径**：`I:\极简遥控器` → 新机可能是 `D:\projects`，计划里逐条给出映射；
- **会话 `cwd`**：同版本复制文件时，会话首帧的 `cwd` 是绝对路径，需要按映射改写；
- **必须挂工作区**：`workspaceRegistry` 只在首次启动按 cwd 引导一次分组，之后不自动收编。
  导入的会话必须显式 `create(path,title)` + `attachSession(id)`，且 `cwd` 与 `workspace.path`
  **逐字一致**（分隔符、大小写规范化），否则"对话在、界面上看不见"；
- **附件不用映射**：内容寻址（`attachments/v1/objects/<sha256>`），按对象树复制即可；
- 正文里的旧路径**不改**，结果里如实说明。

## 七、跨版本迁移（次选路径）

只有当两端 DSH 版本不一致时才走服务重建：

- 用 `ctx.get('sessionPersistence')` 的 `list()` / `open(id,'read')` / `read(offset,length)` 读事件流；
  **必须分片读**（本机最大单会话 55.9 MB zstd，解压后可能数百 MB）；
- 重编码时要归一：header 白名单（多余字段会被拒）、`cwd` 必须绝对路径、
  `isSeeded:false` 配 `inheritedEventCount:0`、surface 事件的 `surfaceOp` 拼写随版本不同；
- 写入优先 **`ctx.agents.create({ sessionId, meta, seed, agentOptions, setup })`**：它会让会话
  即时出现在界面、并绑好预设与默认模型；`sessionPersistence.create` 只作兜底（只落盘，界面要刷新才见）；
- **id 冲突**：命中 `SessionAlreadyExistsError` 就另铸新 id 重试（不能覆盖）；
- 父会话没一起导入时，子会话会成孤儿：父在包内才保留 `parentSession`，否则丢弃并记一条。

## 九之二、兼容性与「目标机已装同款插件」

这两件事直接决定导入会不会把 profile 弄坏，必须写进计划里。

**兼容性门槛**（官方 app-boot）：

- 包声明了 `engines.dsh`：**只看这个范围**，忽略 `peerDependencies`；
- 没声明：`@deepseek-ai/dsh` 与所有 `@deepseek-ai/dsh-*` 的每个 peer 范围都必须匹配；
- 豁免记录在 profile 的 `compatibility.json`（不在 `package.json`）；
- 不匹配的 bundle 会被**跳过**并记入 `skippedBundles`，启动时打印一次；
- **但 profile 与用户 patch 的错误仍然会让启动失败** —— 所以 patch 比 bundle 更要命。

**已装同款包**（官方 plugin-manager）：

- `installBundle(spec)` 命中已安装包时**直接失败**（`error.code: 'already-installed'`），且不改任何文件；
- 要换版本或换来源：先 `removeBundle(name)`，再 `installBundle(spec)`；
- 有 HMR 时删装后无需重启；没有 HMR 时装完返回 `restart-required`；
- 所以导入计划必须区分三种情况：**未装 → 装；已装同版本 → 跳过；已装不同版本 → 先删后装**。

**会话格式**（官方 session-format-status）：当前 writer 为 **v4**，v4 已是「已发布格式」
（release record 指向 `dsh-v0.2.0-rc.2`）。两端同为 v4 时可直接复制会话文件；
跨版本要按官方迁移规则处理，不能想当然重编码。

## 九之三、P3 实测记录（会话文件格式）

- 会话日志是**多个 zstd 帧首尾相接**的追加文件：第一帧是头部（含 `cwd`），后面每批事件一帧。
- 实测：一份 26,039 字节的文件用 `zlib.zstdDecompressSync` **只解出第一帧**（187 字节）。
  所以改写 cwd 的正确做法是「解第一帧 → 改 → 重压 → 与其余字节拼接」，而不是整份重编码。
- 帧边界用「扫魔数 + 解压验证」定位，不解析 zstd 块信息（出错面小得多）。
- 目标目录名由路径生成：`D:\X\X` → `--D-X-X--`（去盘符冒号、分隔符折成 `-`、首尾各包 `--`）。
- 端到端实测：真机导出一份 36 MB 会话，包内首帧可解、cwd 一致。

## 十、P0 风险（必须当成一等要求）

1. **空或畸形的 patch 会让 DSH 起不来**：README 明确"空文件或仅含注释的文件会导致启动失败，要禁用请写 `[]`"。
   结论：**写入前校验、写入后解析回读、始终留 `.bak`**，且合并产物必须是有效非空数组。
2. **与 HMR 抢写**：profile patch 会被 live 重载。裸写文件会绕过 plugin-manager 的串行队列，
   导入途中被重载 = 半套状态。**必须走服务**；确实要裸写时，先要求停止该 profile 实例。
3. **不装插件时不能因为缺 bundle 就砖**：app-boot 会跳过解析失败的 bundle 并记入 `skippedBundles`，
   但 **profile 与用户 patch 的错误仍会导致启动失败** —— 所以 patch 的正确性比 bundle 更要命。
4. **静默跳过不可接受**：settings 条目不存在、bundle 被跳过、装包失败，全部要计数并逐条列出。

## 十一、验收判据（可执行，不是"看起来对"）

- `ctx.pluginManager.listBundles()`：每个目标 bundle 存在且无 error；
- `ctx.settings.describe(ns)`：抽检关键 namespace 的值与 revision；
- `ctx.get('sessionPersistence').list()`：会话数量 = manifest 里声明的数量；
- `workspaceRegistry.list()`：目标工作区存在，且 `attachSession` 过的会话数对得上；
- 附件抽查：随机几个 `sha256` 对象在目标机存在且大小一致；
- patch 回读：两层都能被 YAML 解析，且不是空数组。

## 十二、不做的事

- 不自动重启 DSH。
- 不搬运凭据值，除非人工在界面开。
- 不做"边跑边覆盖"：导入必须在可回滚前提下进行。
- 不承诺正文路径一致：只保证工作区与 `cwd` 一致，其余如实说明。
- 不搬 cache / logs / 浏览器 localStorage。
- 不把"装别的插件"写进流程。

## 十三、设置页里的移魂面板

移魂功能在遥控设置页里有一个可收起/展开的板块，默认收起，展开后按「导出 / 导入 / 高级 / 状态」四组给出可选项。

### 面板结构

**移魂**（默认收起，摘要显示上次导出/导入状态）

- **导出**
  - 包含内容勾选：仅结构+配置 / 加插件包 / 加会话 / 加附件 / 含凭据但不含值
  - 输出位置：目录路径输入框 + 「选择目录」按钮
  - 导出前先显示预计体积（分级提示：结构+配置约 X MB / 加会话约 Y GB / 加附件约 Z GB）
  - 「开始导出」按钮 + 进度条 + 结果（成功/失败/部分跳过）

- **导入**
  - 选择灵魂包：路径输入框 + 「选择目录」按钮
  - 体检结果：版本、冲突、缺失依赖（只读显示）
  - 计划预览：会装哪些包、写哪些配置、哪些跳过（只读显示）
  - 「执行导入」按钮（二次确认）+ 进度条 + 结果
  - 「回滚」按钮（二次确认，仅在导入后可用）

- **高级**
  - 路径映射：旧前缀 → 新前缀，逐条输入（例如 `I:\极简遥控器` → `D:\projects`）
  - 兼容性检查开关：开/关（默认开）
  - 跳过项清单：只读显示哪些项被跳过及原因
  - 快照管理：列出最近快照，支持回滚到指定快照

- **状态**
  - 上次导出：时间、结果、体积
  - 上次导入：时间、结果、体积
  - 「需要重启 DSH」提示（如果有）
  - 最近一次导出的体积

### 交互约束

- **默认收起**：参照现有设置页惯例（`settingsGroup` 的 `alwaysOpen=false`），移魂板块默认收起，展开状态在同一次运行内记住，重开回到收起。
- **危险动作二次确认**：导入和回滚必须二次确认，确认文案要点明影响面（例如「导入会覆盖现有配置，是否继续？」「回滚会恢复到导入前的状态，是否继续？」）。
- **失败与部分跳过可见**：结果区域必须显示成功、失败、部分跳过三种状态，不能只显示成功。
- **页面不能替代命令行**：agent 也能用同样的五个工具（`soul_export` / `soul_inspect` / `soul_plan` / `soul_apply` / `soul_rollback`）完成同一件事，界面只是另一种入口。

### 现有设置页惯例（读到的 3 条）

1. **分组与折叠**：`settingsGroup` 统一处理大类外壳，`collapsibleSub` 处理小分类；默认收起，展开状态在同一次运行内记住。
2. **状态显示**：`statusPill` 统一状态标签（已连接/连接中/失败/未开启）；`formatTime` 统一时间戳格式化。
3. **危险操作确认**：`confirming` 状态 + 二次确认按钮（如「确认撤销」/「取消」），确认文案要点明影响面。

### 做不到或需要确认的地方

- **体积预估**：导出前显示预计体积需要提前扫描会话和附件目录，可能耗时较长；未确认是否能在合理时间内完成。
- **路径映射**：路径映射的逐条输入需要用户手动填写，未确认是否有更友好的方式（如自动检测常见前缀）。
- **快照管理**：快照管理需要持久化存储快照信息，未确认现有设置页是否有持久化存储能力。
